# 🍎 Autonomous Search & Rescue — 팀 해커톤 결과물

> 사전 지도가 없는 아파트 환경에서, 로봇이 **스스로 탐색 → 빨간 사과 2개 발견 → 방문 → 출발점 복귀**까지 수행하도록 만든 Webots 자율주행 컨트롤러입니다.

## 1. 전체 개요

| 항목 | 내용 |
|---|---|
| 주제 | Autonomous Search & Rescue (미지의 환경 탐색 → 대상 식별 → 방문 → 시작점 복귀) |
| 환경 | Webots 시뮬레이션, `apartment.wbt` (약 13 × 18 m) |
| 로봇 | TurtleBot3 (Differential Drive). LiDAR `LDS-01`(360빔), 카메라, 나침반(compass), 바퀴 엔코더 |
| 구조 대상 | 빨간 사과 2개 (지름 약 10 cm) |
| 평가 항목 | 목표 달성, 기술 구현, 주행 안정성, 창의성 |
| 언어 / 라이브러리 | Python, NumPy, OpenCV, Ultralytics YOLO (`yolo11n.pt`) |
| 핵심 제약 | IMU 없음, 사전 지도 없음, 사과는 바닥의 작은 물체 (LiDAR로는 보이지 않음) |

**해결 방식 한 줄 요약**

> LiDAR로 지도를 쌓고 → 지도의 "아는 곳과 모르는 곳의 경계(frontier)"로 이동하며 탐색하고 → 카메라(YOLO + 색상)로 사과를 찾아 → A\*로 경로를 만들어 → 안전장치를 거친 뒤 바퀴를 움직입니다.

## 2. 역할 분담

팀은 4개 역할로 나누어 **파일 단위로 소유권**을 정하고, 모듈 사이 입출력 형식을 먼저 합의한 뒤 병렬로 개발했습니다.

| 역할 | 담당 | 소유 파일 | 한 줄 설명 |
|---|---|---|---|
| **A. 매핑** | 지도 작성 | `lidar.py`, `static_mapping.py`, `map_view.py` | LiDAR 점유 격자 지도를 만들고 시각화 |
| **B. 위치 추정·통합** | 위치, 미션, 전체 연결 | `config.py`, `data_types.py`, `pose.py`, `robot_io.py`, `localization.py`, `mission.py`, `rescue_controller.py` | 센서 → 위치 → 지도 → 계획 → 모터 전체 루프 연결, 미션 상태 관리 |
| **C. 객체 탐지** | 사과 탐지·관리 | `target_detection.py`, `target_manager.py` | 카메라에서 사과를 찾고 위치를 계산, 중복 제거·방문 기록 |
| **D. 경로·주행** | 길 찾기와 이동 | `global_planner.py`, `drive.py`, `safety.py`, `exploration.py`, `navigation.py`, `test_d_role.py` | 목적지까지 경로를 만들고, 따라가고, 충돌 직전에 멈춤 |

> 모듈 사이 약속
> - 좌표: `x`는 앞쪽, `y`는 왼쪽, `theta`는 반시계 방향이 + (단위: m, rad)
> - 지도: `occ[row][col]` = `-1` 미확인 / `0` 빈칸 / `1` 장애물, 한 칸 0.1 m
> - 경로: 월드 좌표 `(x, y)` 리스트, 경로가 없으면 `[]`
> - 바퀴 명령: `(left, right)` rad/s

## 3. 실행 방법

1. **Webots**에서 `worlds/apartment.wbt` 를 연다. (`File → Open World`)
2. 로봇 노드의 `controller` 값을 `rescue_controller` 로 지정한다.
3. 필요한 패키지를 설치한다. (Webots가 사용하는 Python에 설치해야 한다.)

   ```bash
   pip install numpy opencv-python ultralytics
   ```

4. Webots의 `Tools → Preferences → General → Python command` 에 위 패키지를 설치한 Python 경로를 지정한다.
5. 재생 ▶ 을 누르면 콘솔에 `[MISSION] HOME 저장` 이 출력되고 탐색이 시작된다.
6. 종료 시 `final_map.png` 로 마지막 점유 격자 지도가 저장된다. (OpenCV 창으로 실시간 지도도 표시)

**콘솔 로그 의미**

| 로그 | 의미 |
|---|---|
| `[MISSION] EXPLORE / TARGET / RETURN / DONE` | 현재 미션 상태 |
| `[TARGET] 관측: ...` | 사과 후보 좌표 등록·갱신 |
| `[TARGET] 방문 n/2` | 사과 방문 처리 |
| `[PATH] 좁은 통로: 0.xx m 여유` | 좁은 곳을 지나려고 벽 여유를 줄여서 재계획 |
| `[PATH] 경로 없음: ...` | A\*가 경로를 찾지 못함 (원인 포함) |

**D 모듈 단독 테스트 (Webots 없이)**

```bash
cd controllers/rescue_controller
python test_d_role.py
```

## 4. 전체 동작 흐름

컨트롤러는 시뮬레이션 한 스텝(약 64 ms)마다 아래를 반복합니다.

```
 ┌───────────────────────────────────────────────────────────────────┐
 │ 1. robot_io        엔코더·compass·LiDAR·카메라 읽기               │
 │ 2. localization    바퀴 이동량 + 방향으로 pose(x, y, theta) 추정   │
 │ 3. static_mapping  LiDAR 광선으로 점유 격자 지도 갱신              │
 │ 4. target_detection 5스텝마다 카메라에서 빨간 사과 후보 탐지        │
 │    target_manager   월드 좌표로 변환, 중복 병합, 방문 판정          │
 │ 5. mission         EXPLORE / TARGET / RETURN / DONE 선택          │
 │ 6. exploration     (탐색 중) 다음 frontier 목적지 선택             │
 │    navigation      지도를 팽창해 통행 불가 영역 생성 → A* 경로      │
 │ 7. drive           경로를 따라가는 (left, right) 바퀴 속도         │
 │ 8. safety          최신 LiDAR로 최종 검사: 감속·정지·후진·회전     │
 │ 9. robot_io        바퀴에 명령 전달                                │
 └───────────────────────────────────────────────────────────────────┘
```

**미션 상태 전환**

```
 EXPLORE ──사과를 2회 이상 관측──▶ TARGET ──0.42 m 이내 접근──▶ 방문 처리
    ▲                                  │
    └────── 미방문 사과 없음 ◀──────────┘
 사과 2개 모두 방문 ──▶ RETURN ──출발점 0.18 m 이내──▶ DONE
```

**재계획 시점**: 목표/상태가 바뀔 때, 사과를 방문했을 때, 안전장치가 오래 막혔을 때, 그리고 12스텝마다.

## 5. 역할별 파일과 동작 방식

### A. 매핑 — `lidar.py`, `static_mapping.py`, `map_view.py`

- **`lidar.py`**: LDS-01의 빔 번호를 로봇 기준 각도로 바꿉니다. 실측으로 확인한 규칙은 **180번 = 앞, 90번 = 왼쪽, 270번 = 오른쪽** 이며 번호는 시계 방향으로 증가합니다.
- **`static_mapping.py`**: 300 × 300칸(30 m × 30 m), 한 칸 0.1 m의 점유 격자입니다.
  - 광선이 지나간 칸은 "빈칸" 증거를 쌓고, 광선 끝은 "벽" 증거를 쌓습니다 (**log-odds**).
  - 증거가 충분히 쌓여야 칸의 상태가 바뀌므로, 스치듯 지나간 광선 하나가 벽을 지우지 못합니다.
  - 최대 거리(3.5 m)까지 닿은 광선은 "벽 없음"으로 처리합니다.
- **`map_view.py`**: 지도·로봇·경로·사과 후보를 실시간으로 그리고 종료 시 PNG로 저장합니다. 그리다가 오류가 나도 로봇 제어는 멈추지 않도록 예외를 모두 삼킵니다.

### B. 위치 추정·통합 — `robot_io.py`, `localization.py`, `mission.py`, `rescue_controller.py`

- **`robot_io.py`**: 장치 이름은 `config.py`에서만 읽고, 모터를 속도 모드로 전환하고 센서를 켭니다. 바퀴 명령이 한계(3.0 rad/s)를 넘으면 **좌우 비율을 유지한 채 함께** 줄여 회전 모양이 바뀌지 않게 합니다.
- **`localization.py`**: 엔코더로 이동 거리를, compass로 방향 변화를 구해 시작점 기준 `(x, y, yaw)`를 누적합니다. 방향은 구간 중간값(`yaw + Δyaw/2`)으로 적분해 오차를 줄이고, 값이 `NaN`이면 예외를 냅니다.
- **`mission.py`**: 시작 위치를 저장하고 `EXPLORE → TARGET → RETURN → DONE` 상태를 결정합니다.
- **`rescue_controller.py`**: 위 모듈을 하나의 `step` 루프로 연결하는 컨트롤러 본체입니다. 좁은 통로에서는 벽 여유를 `0.23 → 0.18 → 0.14 m` 순으로 줄이며 재계획합니다.

### C. 객체 탐지 — `target_detection.py`, `target_manager.py`

- **`target_detection.py`**: 두 단계로 사과를 찾습니다.
  1. **YOLO(`yolo11n`) + 색상 검증**: COCO의 `apple` 클래스로 후보를 찾고, 박스 안쪽 70%의 **HSV 빨간 픽셀 비율이 15% 이상**일 때만 인정합니다. (초록·주황·보라 사과 제외)
  2. **색 + 모양 보조 검출**: YOLO가 못 잡으면 진한 빨강 영역의 **원형도(circularity) ≥ 0.6**, 가로세로 비율, 화면 가장자리·천장 쪽 제외 조건으로 후보를 찾습니다.
  - 방향(bearing)은 박스 중심과 카메라 FOV로, 거리는 **사과 지름(10 cm)과 박스 폭으로 계산하는 핀홀 공식**으로 구합니다. 일부만 보이면 거리를 만들지 않습니다.
- **`target_manager.py`**: 관측을 월드 좌표로 변환(`pose + 거리·방향`)하고, 0.6 m 이내는 같은 사과로 보아 **평균으로 위치를 다듬습니다.** 2번 이상 관측되어야 목표로 인정하고, 0.42 m 이내로 접근하면 방문 처리하며 방문한 사과는 다시 선택하지 않습니다. 카메라 거리가 없으면 해당 방향의 LiDAR 거리를 중앙값으로 대신 쓰고, 둘 다 믿을 수 없으면 좌표를 만들지 않습니다.

### D. 경로·주행 — `global_planner.py`, `drive.py`, `safety.py`, `exploration.py`, `navigation.py`

- **`global_planner.py`**: 4방향 **A\*** (맨해튼 거리 휴리스틱). 시작/목표가 막혔거나 지도 밖이면 탐색 없이 `[]`을 돌려줍니다. 그 외에 목표가 벽이면 가장 가까운 빈칸으로 옮기는 `nearest_free_cell`, 경로 위에 새 벽이 생겼는지 보는 `path_is_blocked`, 장애물 팽창 `inflate`, 벽 여유를 단계적으로 줄이는 `plan_progressive`를 제공합니다.
- **`navigation.py`**: 점유 격자를 **통행 불가 지도**로 바꾸는 어댑터입니다. 미확인 칸도 통행 불가로 보고, 장애물을 `clearance`(로봇 반경 + 여유)만큼 부풀립니다. 사과 목표는 사과 자체가 장애물 칸일 수 있어 **반경 안의 갈 수 있는 칸 중 실제로 경로가 있는 곳**을 도착점으로 삼습니다.
- **`drive.py`**: **look-ahead 경로 추종**입니다.
  - 경로에서 일정 거리(0.15 m) 앞의 점을 목표로 삼고, 로봇 좌표계로 변환해 방향 오차를 구합니다.
  - 오차가 60°보다 크면 제자리 회전, 작으면 곡률(`2·y / d²`)로 전진하며 회전합니다.
  - 급커브와 목표 근처에서는 속도를 줄입니다. (기본 0.10 m/s. 0.18 m/s에서는 벽을 긁어 낮춤)
  - `(v, w)` → `(left, right)` 변환은 `v ± w·L/2 / r` 이고 `WHEEL_BASE = 0.177 m`, `WHEEL_RADIUS = 0.033 m`입니다.
  - `Sweep`: 목표 지점에 도착하면 **제자리에서 한 바퀴 돌며** 카메라로 주변을 훑습니다.
- **`safety.py`**: drive 출력과 바퀴 사이의 **마지막 방어선**입니다. 정면 ±15빔의 최소 거리를 보고
  - `0.40 m` 이내 → 거리에 비례해 감속
  - `0.20 m` 이내 → 전진 금지, 열린 쪽으로 회전
  - 계속 막히면 → 재계획 요청, 더 오래 막히면 **약 15 cm 후진 → 약 90° 회전** 탈출 동작
  - 뒤가 막혀 있으면 후진하지 않음
- **`exploration.py`**: **frontier 탐색**. 아는 빈칸 중 모르는 칸과 맞닿은 칸을 찾아 덩어리로 묶고, 작은 덩어리(센서 잡음)는 버린 뒤 **가깝고 넓은 열린 곳**에 점수를 줘서 고릅니다. frontier가 떨어지면 **아직 안 본 구역(커버리지)** 으로 이동하며, 실패한 목표는 기억해서 다시 고르지 않습니다.

## 6. 사용한 핵심 개념

| 개념 | 쓰인 곳 | 쉬운 설명 |
|---|---|---|
| **Differential Drive 운동학** | `drive.py` | 양쪽 바퀴 속도 차이로 회전. `(v, w)` ↔ `(left, right)` 변환 |
| **Dead reckoning (오도메트리)** | `localization.py` | 바퀴 회전량으로 위치를 누적 추정. 오차가 쌓이는 것이 약점 |
| **좌표 변환** | `static_mapping.py`, `target_manager.py` | 로봇 기준(거리, 각도)을 지도 기준 `(x, y)`로 변환 |
| **Occupancy Grid** | `static_mapping.py` | 방을 격자로 나눠 빈칸/벽/미확인 표시 |
| **Log-odds 갱신** | `static_mapping.py` | 증거가 쌓여야 칸의 상태가 바뀌어 노이즈에 강함 |
| **Inflation (장애물 팽창)** | `navigation.py` | 벽을 로봇 크기만큼 부풀려 로봇을 점으로 취급 |
| **A\* 경로 탐색** | `global_planner.py` | `f = g + h`, 목표 방향을 우선해 최단 경로 탐색 |
| **Look-ahead 추종** | `drive.py` | 앞쪽 점을 계속 따라가 부드럽게 주행 |
| **Frontier 탐색** | `exploration.py` | 아는 곳과 모르는 곳의 경계가 다음 목적지 |
| **Coverage 탐색** | `exploration.py` | 안 본 구역을 블록 단위로 기억해 구석까지 확인 |
| **Reactive safety layer** | `safety.py` | 지도와 무관하게 최신 LiDAR만으로 정지·탈출 |
| **객체 탐지 (YOLO) + 색 검증** | `target_detection.py` | 딥러닝 후보를 색으로 한 번 더 거름 |
| **핀홀 카메라 거리 추정** | `target_detection.py` | 알려진 크기(10 cm)와 화면상 폭으로 거리 계산 |
| **상태 기계 (FSM)** | `mission.py` | 탐색 → 방문 → 복귀 단계 관리 |
| **센서 융합** | `target_manager.py` | 카메라 방향 + LiDAR/핀홀 거리로 위치 확정 |

## 7. 겪은 문제와 극복 과정

| 문제 | 원인 | 해결 |
|---|---|---|
| 벽을 긁거나 끼임 | 안전 거리와 경로 벽 여유가 서로 달랐고, 속도 0.18 m/s는 너무 빨랐음 | 속도를 0.10 m/s로 낮추고, 정지 거리를 **경로 벽 여유와 맞춰** 재설정. 시행착오 끝에 정지 `0.20 m`, 감속 `0.40 m`로 확정 |
| 좁은 문틀에서 "경로 없음" | 팽창 반경이 커서 통로가 막힘 | 벽 여유를 **`0.23 → 0.18 → 0.14 m` 순으로 단계적으로 줄이며** 재계획. 로봇 반경(0.105 m) 아래로는 내리지 않음 |
| 문턱에서 제자리 360° 회전 | 양옆이 가까운 곳에서 sweep가 시작됨 | 양옆 0.32 m 이내면 sweep를 건너뛰고 다음 탐색 지점을 고름 |
| 막힌 뒤 같은 곳에서 반복 | 정지만 하고 빠져나오는 동작이 없었음 | **15 cm 후진 + 90° 회전**(열린 쪽으로) 탈출 시퀀스 추가 |
| 사과가 거의 안 잡힘 | YOLO nano가 바닥의 작은 사과를 약 20% 프레임만 검출 | 색상·원형도 기반 **보조 검출**을 추가하고, 카메라 프레임을 따로 수집해 임계값을 튜닝 (`cam_probe/`) |
| 사과 거리 오차 | LiDAR 높이에 사과가 없어 바닥 사과는 LiDAR에 안 보임 | **사과 지름 10 cm 기반 핀홀 거리**를 우선 사용, 신뢰할 수 없으면 좌표를 만들지 않음 |
| 같은 사과가 여러 개로 등록 | 관측 오차 | 0.6 m 이내 병합 + 평균으로 좌표 보정, **2회 이상 관측**돼야 목표 인정 |
| 한 번의 스친 광선으로 벽이 사라짐 | 단순 덮어쓰기 지도 | **log-odds**로 증거가 쌓여야 상태 변경 |
| 지도 범위 밖으로 로봇이 나감 | 기본 지도 10 m는 아파트(13 × 18 m)보다 작음 | 지도 크기를 **300칸(30 m)** 으로 확장 |
| 모듈 병합 시 이름·좌표계 충돌 | 팀원마다 `yaw`/`theta`, `AXLE`/`WHEEL_BASE` 이름이 달랐음 | `Pose.theta` 별칭, `config.py` 이름 호환 처리, 입력 형식 합의 |
| 잘못된 입력에 컨트롤러가 죽음 | `NaN` pose, 지도보다 큰 팽창 등 | D 모듈 전체에 **방어 코드와 단독 테스트(`test_d_role.py`)** 추가 |

## 8. 검증과 현재 결과

**검증 방법**

- `test_d_role.py`: A\*·팽창·단계적 계획·경로 추종·안전장치·frontier 탐색을 Webots 없이 검증하는 단위 테스트
- `controllers/d_test/`: 임시 목표 왕복 시험. 로그에서 **나가는 경로와 돌아오는 경로 모두 도착 오차 약 0.13~0.15 m, 소요 시간 약 20.7초** 를 기록했습니다. 이후 frontier 탐색 구간에서는 좁은 곳에서 끼임 로그가 확인되어 안전장치를 보강했습니다.
- `controllers/final_run/`: 실제 컨트롤러를 수정 없이 실행하며 safety/drive/explorer/A\*의 판단을 추적하는 로그 도구
- `controllers/cam_probe/`: 카메라 프레임을 모아 빨간 영역·원형도 임계값을 튜닝하는 도구

**마지막 통합 실행 결과 (정직한 기록)**

| 단계 | 결과 |
|---|---|
| 출발점 저장, 탐색 시작 | ✅ 동작 |
| frontier 탐색, 좁은 통로 통과 | ✅ 벽 여유를 단계적으로 줄이며 동작 |
| 사과 관측과 좌표 등록 | ✅ 동작 |
| 사과 방문 | ⚠️ **1/2** 방문 확인 |
| 두 번째 사과 접근 | ❌ `TARGET: no_path` 가 반복되며 제자리 회전에 갇힘 |
| 출발점 복귀 (`RETURN` → `DONE`) | ❌ **로그상 도달하지 못함** |

즉, **"탐색 + 지도 작성 + 사과 탐지 + 일부 방문"까지는 동작**했지만 **2개 방문과 복귀까지의 완주는 최종 실행에서 확인하지 못했습니다.** 아래 한계에 원인과 보완 계획을 적었습니다.

## 9. 한계와 앞으로 보완할 점

**알려진 한계**

1. **두 번째 사과로 가는 경로 실패.** 최종 로그에서 `TARGET: no_path`가 반복되었습니다. 원인을 하나로 확정하지는 못했지만, 사과가 벽·가구 가까이에 있어 팽창된 통행 불가 영역에 접근 가능한 칸이 모두 가려졌거나, 사과 좌표 추정이 벽 쪽으로 치우쳤을 가능성이 가장 큽니다.
2. **갇혔을 때의 최종 탈출 전략이 없음.** 경로가 없으면 제자리 회전(`-0.7, 0.7`)만 반복합니다. 재시도 횟수 제한이나 다른 목표로 넘어가는 로직이 없습니다.
3. **오도메트리 누적 오차.** 엔코더와 compass만 쓰므로 오래 주행할수록 지도가 조금씩 어긋날 수 있습니다.
4. **정적 장애물 위주.** 움직이는 사람을 따로 추적하는 모듈(`obstacle_tracker`, `dynamic_mapping`)은 구현하지 못했고, 가까운 장애물에 대한 **감속·정지(safety)** 로만 대응합니다.
5. **YOLO nano의 한계.** 바닥의 작은 사과를 자주 놓쳐 색상 기반 보조 검출에 의존하고, 조명·가림에 약할 수 있습니다.
6. **4방향 A\*와 격자 경로.** 경로가 각져서 주행이 부드럽지 않고, 속도(0.10 m/s)가 느려 시간 제한이 있으면 불리합니다.
7. **파라미터가 이 월드에 맞춰 튜닝됨.** 다른 월드에서는 정지 거리·벽 여유·색상 임계값을 다시 맞춰야 합니다.

**보완 계획 (우선순위 순)**

| 우선순위 | 보완 내용 | 기대 효과 |
|---|---|---|
| 1 | 목표 주변 접근 칸 탐색 범위를 단계적으로 넓히고(`approach` 확대, 마지막엔 팽창 해제), 접근에 실패한 목표는 보류 후 다른 사과·탐색을 먼저 수행 | `no_path` 갇힘 해소 |
| 2 | `no_path`가 N회 반복되면 위치를 옮기며 **다른 각도에서 재접근**, 일정 시간 진전이 없으면 **복귀 우선** | 최소한 복귀까지는 보장 |
| 3 | **제한 시간 기반 복귀**: 시간이 일정 이상 지나면 사과 수와 관계없이 출발점으로 돌아가기 | 점수 안정화 |
| 4 | LiDAR 스캔 매칭 등으로 위치 보정 | 지도 어긋남 감소 |
| 5 | 연속 스캔 비교로 움직이는 물체를 추적하고 예상 위치를 임시 위험 영역으로 사용 | 사람 회피 |
| 6 | 8방향 A\* 또는 경로 평활화, 직선 구간 속도 상향 | 더 빠르고 부드러운 주행 |
| 7 | 사과용 소형 모델 재학습 또는 색상 임계값 자동 보정 | 탐지 안정화 |

## 10. 우리만의 아이디어

1. **좁은 곳을 위한 "단계적 벽 여유"**: 처음엔 넉넉한 여유(0.23 m)로 안전하게 계획하고, 길이 없을 때만 `0.18 → 0.14 m`로 줄입니다. 안전과 통과 가능성을 둘 다 잡습니다.
2. **Frontier + Coverage 이중 탐색**: 아는 곳의 끝(frontier)을 먼저 가고, 끝나면 **"카메라로 실제로 본 구역"을 블록 단위로 기록**해 안 본 구석까지 확인합니다. 작은 사과가 구석에 있어도 놓치지 않기 위한 설계입니다.
3. **YOLO + 색상 이중 검출**: 딥러닝의 일반성과 색·모양 규칙의 안정성을 합쳤습니다. 둘 다 거리를 못 구하면 **억지로 좌표를 만들지 않습니다.**
4. **세 겹 안전 구조**: 지도 팽창(사전 예방) → 경로 재계획(반응) → LiDAR safety(최후 방어, 후진+회전 탈출). 지도가 틀려도 마지막 층이 막아 줍니다.
5. **방어적 모듈 설계**: 잘못된 입력(`NaN`, 지도 밖 좌표)에도 컨트롤러가 죽지 않고 안전하게 멈추도록 하고, 지도 뷰어 같은 부가 기능은 실패해도 주행에 영향이 없게 분리했습니다.
6. **측정 기반 튜닝 도구 자체 제작**: `cam_probe`(카메라 프레임 수집·임계값 평가), `final_run`(판단 과정 추적 로그), `test_d_role`(단위 테스트)로 **감이 아니라 기록으로** 파라미터를 정했습니다.

## 11. 느낀 점

- **통합이 가장 어려웠습니다.** 각자 만든 모듈은 단독으로는 잘 돌았지만, 합치는 순간 좌표 방향, 이름(`yaw`/`theta`), 단위가 어긋났습니다. 코딩 전에 **입출력 형식을 먼저 합의하는 것**이 알고리즘보다 중요하다는 걸 배웠습니다.
- **시뮬레이션에서도 "현실의 문제"가 그대로 나옵니다.** 센서 잡음, 누적 오차, 좁은 통로, 작은 물체 탐지 같은 문제는 이론으로 아는 것과 직접 부딪히는 것이 완전히 달랐습니다.
- **안전이 곧 성능입니다.** 빠르게 가는 것보다 벽에 끼지 않고 끝까지 가는 것이 점수에 중요했고, 속도를 낮추고 안전장치를 다듬을수록 오히려 완주 가능성이 올라갔습니다.
- **로그가 가장 좋은 디버거였습니다.** "왜 안 가지?"를 추측하는 대신 판단 과정을 기록해 보니 원인이 훨씬 빨리 보였습니다. 이번 최종 실행의 `no_path` 반복도 로그 덕분에 원인을 좁힐 수 있었습니다.
- **완벽한 결과보다 정직한 기록.** 완주하지 못한 부분을 숨기지 않고 한계와 보완 계획으로 적어 두는 과정이, 다음에 무엇을 고쳐야 하는지 가장 분명하게 알려 줬습니다.
- **짧은 시간의 협업을 경험했습니다.** 역할을 나누고, 브랜치로 작업하고, 충돌을 해결하며 병합하는 과정까지 한 번에 경험한 값진 시간이었습니다.
